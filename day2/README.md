# День 2 — формат ответа

Один и тот же запрос уходит в модель дважды: свободным и зажатым ограничениями.
Ответы показываются рядом, а к каждому прикладывается проверка — соблюдён формат или нет.
Отдельная кнопка прогоняет зажатый запрос несколько раз подряд и сверяет структуру ответов
между собой.

Развитие [дня 1](../day1): клиент к DeepSeek, показ сырого HTTP-обмена и дизайн-система
переиспользованы, добавлены ограничения формата и сравнение.

## Стек

## Три рычага контроля

Каждый включается отдельным переключателем. Выключенный не попадает ни в промпт, ни в запрос к API.

**1. Описание формата** — `FREE` / `JSON` / `BULLETS` / `TABLE` / `SENTENCE`.
Для JSON задаётся схема-скелет; она же служит эталоном при проверке ключей ответа.
Отдельно включается `response_format: json_object` — режим, в котором валидный JSON
гарантирует сам провайдер.

**2. Ограничение длины** — потолок слов и пунктов уходит инструкцией в system-prompt,
`max_tokens` — параметром API. Разница существенная: инструкцию модель соблюдает по смыслу
и заканчивает мысль, `max_tokens` рубит ответ на полуслове (`finish_reason: length`).

**3. Условие завершения** — стоп-последовательность (провайдер обрывает генерацию сам)
и/или явная инструкция закончить маркером. Работают независимо и хорошо сочетаются:
инструкция заставляет модель поставить маркер, стоп-последовательность гарантирует,
что после него ничего не придёт.

Собранный из переключателей system-prompt показывается в интерфейсе целиком.

**Температура** задаётся тремя пресетами (`0.0` точный, `1.0` обычный, `1.5` творческий)
и слайдером для промежуточных значений — вписать недопустимое значение руками нельзя.
Числовые поля лимитов зажимаются в диапазон, который принимает API, поэтому запрос не
уходит заведомо невалидным.

## API

### `POST /api/compare`

```json
{
  "prompt": "Дай рецепт борща на 4 порции",
  "model": "deepseek-chat",
  "params": { "temperature": 0 },
  "constraints": {
    "format": "JSON",
    "jsonSchema": "{\"dish\":\"string\",\"ingredients\":[{\"name\":\"string\",\"weightGrams\":\"number\"}]}",
    "jsonMode": true,
    "maxWords": 150,
    "maxItems": null,
    "maxTokens": 600,
    "stopSequence": "###",
    "endMarkerInstruction": true,
    "endMarker": "###"
  }
}
```

Возвращает `baseline` и `constrained` — два прогона одного запроса. Эталонный идёт
без system-prompt, без `max_tokens` и без стоп-последовательности, но проверяется теми же
мерками: видно, что без инструкций формат не соблюдается.

У каждого прогона есть `compliance`:

| Поле | Что показывает |
|---|---|
| `passed` | нарушений не найдено |
| `violations` | список нарушений человеческим языком |
| `words`, `chars`, `lines` | фактический размер ответа |
| `jsonValid` | ответ разобрался как JSON |
| `schemaMissing`, `schemaExtra` | расхождения с заданной схемой по путям вида `ingredients[].weightGrams` |
| `itemCount` | пунктов списка или строк таблицы |
| `endMarkerFound` | маркер стоит в конце ответа |
| `truncated` | ответ обрезан по `max_tokens` |
| `structureSignature` | отпечаток структуры JSON без значений |

### `POST /api/determinism`

То же тело плюс `"runs": 3` (от 2 до 8). Прогоняет зажатый запрос N раз параллельно
и группирует ответы по структурной подписи.

```json
{
  "runs": 4,
  "structureGroups": [{ "signature": "{dish:string,ingredients:[{name:string,…}],…}", "count": 4 }],
  "structureIdentical": true,
  "passedCount": 4,
  "allPassed": true
}
```

`structureIdentical: true` означает, что все прогоны вернули одинаковую форму данных —
значения при этом разные. Именно это и есть детерминированный формат.

## Как считается структурная подпись

Ответ парсится в дерево, значения выбрасываются, ключи сортируются:

```
{"dish":"борщ","ingredients":[{"name":"свёкла","weightGrams":300}]}
{"dish":"уха", "ingredients":[{"name":"судак", "weightGrams":500}]}
        ↓ обе дают одну подпись
{dish:string,ingredients:[{name:string,weightGrams:number}]}
```

Разные значения подпись не меняют, а вот пропавшее поле или изменившийся тип — меняют.
Для форматов кроме JSON структуру сравнивать не по чему, поэтому там показывается
только доля прогонов, соблюдающих формат.

## Наблюдения на живых запросах

| Запрос | Без ограничений | С ограничениями |
|---|---|---|
| «Дай рецепт борща на 4 порции» | 473 слова markdown с заголовками | 22 слова валидного JSON по схеме |
| «Как подготовиться к собеседованию» | 794 слова, 31 «пункт» | 63 слова, ровно 5 пунктов |

Проверка стабильности при `temperature: 1.0`, 4 прогона: структура совпала во всех четырёх,
значения различались. Стоп-последовательность срабатывает как задумано — ответ приходит
без маркера, потому что провайдер обрывает генерацию ровно на нём (`finish_reason: stop`).
