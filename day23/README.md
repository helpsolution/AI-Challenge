# День 23 — RAG-агент с локальным реранкером

Использует лекции по системному дизайну из дня 22, структурную нарезку Markdown, локальную Ollama,
SQLite, BGE cross-encoder через llama.cpp и DeepSeek для query rewrite и ответа. Порог релевантности — следующий этап.

## Запуск

Нужны JDK 21, Ollama с `nomic-embed-text`, ключ DeepSeek и сервер реранкера на порту 8012.

Установка llama.cpp и загрузка FP16-модели (около 1,16 ГБ), из каталога `day23`:

```bash
brew install llama.cpp
mkdir -p data/models
curl -fL --retry 3 https://huggingface.co/gpustack/bge-reranker-v2-m3-GGUF/resolve/main/bge-reranker-v2-m3-FP16.gguf -o data/models/bge-reranker-v2-m3-FP16.gguf
llama-server -m data/models/bge-reranker-v2-m3-FP16.gguf --embedding --rerank --pooling rank -c 2048 -b 2048 -ub 2048 --host 127.0.0.1 --port 8012
```

Оставьте сервер в отдельном терминале. В другом запустите агент:

```bash
cd day23
# Если .env ещё нет: cp .env.example .env и вписать DEEPSEEK_API_KEY.
# Документы Markdown с необязательными title и url в YAML лежат в data/corpus/.
./gradlew :rag-agent:bootRun
```

Чат: http://localhost:8241. Трассировки: http://localhost:8241/inside.html.
При первом запуске индекс собирается автоматически. Корпус и `.env` локально скопированы из дня 22;
они, как и SQLite, исключены из Git. После изменения корпуса или настроек индекс пересобирается
при старте. В чате есть кнопка ручной пересборки.

## Компоненты

| Компонент | Ответственность |
|---|---|
| `StructuralChunker` | Markdown → структурные чанки с источником, разделом и offsets |
| `EmbeddingClient` | Тексты и вопрос → векторы Ollama, префиксы задачи и проверка ответа |
| `Indexer` | Корпус → чанки → пачки эмбеддингов → сохранённый индекс |
| `SqliteStore` | Чанки, float32-векторы и метаданные; замена одной транзакцией |
| `KnowledgeBase` | Snapshot индекса в памяти и рейтинг по косинусной близости |
| `Retriever` | Вопрос → эмбеддинг → 20 кандидатов → реранкинг → top-5 |
| `RerankerClient` | Вопрос и фрагменты → оценки локального BGE cross-encoder по HTTP |
| `PromptBuilder` | Правила, история, вопрос и источники → сообщения модели |
| `LlmClient` | Сообщения → ответ DeepSeek |
| `RagRouter` | Решение, нужен ли поиск по лекциям |
| `QueryRewriter` | Вопрос и история → самостоятельный поисковый вопрос через DeepSeek |
| `Agent` | Последовательность вызовов, ответ, источники и трассировка |

## Структурная нарезка

- Заголовки задают границы разделов и путь `Лекция › Раздел › Подраздел`.
- Соседние абзацы внутри раздела собираются вместе; короткие разделы остаются целыми.
- Цель упаковки — 1400 символов, предел содержимого блока — 2200. Это **символы, не токены**;
  префикс задачи, название и путь раздела добавляются отдельно. Ollama вызывается с `truncate=false`:
  превышение контекста модели будет явной ошибкой, а не скрытым обрезанием.
- Обычные списки сохраняются вместе с вводной фразой, насколько позволяет предел. Длинные списки
  делятся по пунктам, вводная фраза повторяется. В глоссарии один термин — один чанк.
- Большая таблица делится по строкам с повторением шапки; большой fenced-блок кода — по строкам
  с восстановлением ограждений. Необычно длинная строка дополнительно делится по доступным границам.
- Длинный абзац делится по предложениям, затем по пробелам; неразрывное длинное слово — последний резерв.
- Чанк хранит исходный `text` и `start/end` в UTF-16, относительно тела документа без YAML.
  `content` добавляет повторённый контекст; `embeddingText` — ещё название и путь раздела.

Произвольного перекрытия в N символов нет. Для списков, таблиц и кода повторяется нужная структура.
Это детерминированная структурная стратегия; семантический анализ через отдельную модель не выполняется.

## Чат и источники

**Авто:** отдельный короткий запрос к DeepSeek решает, нужен ли поиск по лекциям; причина видна в чате.
**По лекциям:** поиск выполняется всегда. **Без RAG:** модель отвечает с историей без поиска.
В браузере хранится история текущего диалога; в следующий запрос передаются последние три успешных
обмена. Обновление страницы очищает диалог. Системные сообщения от клиента не принимаются.
Query rewrite включён по умолчанию и имеет отдельный переключатель. После решения о RAG DeepSeek
формирует самостоятельный поисковый вопрос по текущей реплике и истории: например, «А когда он
не нужен?» после обсуждения ADR → «В каких случаях не нужно создавать ADR?».
Этот вопрос используется для эмбеддинга и BGE-реранкера. Промпт ответа получает исходную реплику
и историю, поэтому поисковая формулировка не подменяет вопрос пользователя.

Переформулировка вызывается с temperature=0 и max_tokens=384, возвращает JSON `query/reason`.
Промпт запрещает отвечать на вопрос, добавлять неподтверждённые факты и менять ограничения.
Код проверяет формат, длину, завершение генерации, сохранение числовых значений и перцентилей.
Это не полная проверка сохранения смысла: отрицания, единицы и намерение контролируются инструкцией
и проверкой результатов эксперимента. При ошибке или некорректном результате используется прежняя
подготовка запроса; причина видна в предупреждении и трассировке. При выключении отдельного вызова
DeepSeek нет. Прежняя подготовка для коротких уточнений просто добавляет предыдущий вопрос;
распознавание кириллицы исправлено, чтобы оно работало и с заглавной «А».
Без RAG query rewrite не вызывается.

В чате есть переключатель «Реранкинг», включённый по умолчанию. При включении отбираются 20
кандидатов по косинусу, затем cross-encoder сортирует их по релевантности и передаёт лучшие 5
в промпт. Он получает вопрос и полный `embeddingText` каждого чанка, включая название и раздел.
При выключении действует прежний top-5 по косинусу. В режиме без RAG реранкер не вызывается.
Если сервер недоступен или вернул некорректные оценки, запрос завершается явной ошибкой; скрытой
подмены реранкинга косинусом нет. Можно выключить переключатель и повторить запрос.

Ссылки `[n]` в ответе раскрывают соответствующий фрагмент. У него показаны раздел, косинус и оценка реранкера,
текст и ссылка на оригинальную лекцию из YAML. Все показанные фрагменты были переданы модели;
метка «В ответе» означает, что модель сослалась на номер. Проверка фактической поддержки утверждений
этим фрагментом автоматически не выполняется. Косинус — мера близости векторов, не вероятность.
Оценки BGE — сырые значения, могут быть отрицательными или больше единицы; это тоже не вероятности.
Ссылки нумеруются в окончательном порядке после реранкинга.

Трассировка содержит решение маршрутизатора, исходный и поисковый вопросы, обмен query rewrite
с DeepSeek, эмбеддинг, кандидатов поиска, их порядок до/после
реранкинга, оценки BGE, промпт и обмен с DeepSeek. Для реранкера сохранён полный HTTP-запрос и ответ.
Ключ замаскирован. Журнал хранит последние 100 запросов в памяти и очищается после перезапуска.
При отсутствии нужной информации агент должен указать, что найденные фрагменты не содержат ответа;
если найдена только часть, показать её и обозначить пробелы.

## Настройки и API

Основные переменные: `DEEPSEEK_API_KEY`, `DEEPSEEK_MODEL`, `DEEPSEEK_BASE_URL`, `OLLAMA_BASE_URL`,
`OLLAMA_EMBED_MODEL`, `PORT`, `RERANKER_BASE_URL`, `RERANKER_TIMEOUT`, `RERANKER_ENABLED`,
`RETRIEVAL_CANDIDATE_K` (20) и `RETRIEVAL_TOP_K` (5). Размеры чанков задаются в `application.yml`.
`QUERY_REWRITE_ENABLED` управляет переформулировкой по умолчанию.
Число кандидатов должно быть не меньше итогового top-K. Изменения реранкинга не требуют пересборки индекса.
При смене embedding-модели проверьте также её документный и поисковый префиксы: текущие настроены
для `nomic-embed-text`. Индекс проверяет корпус, версию нарезки, размеры, модель, URL и префиксы.

```bash
curl localhost:8241/api/knowledge/status
curl 'localhost:8241/api/knowledge/chunks?offset=0&limit=20'
curl -X POST localhost:8241/api/knowledge/rebuild
curl localhost:8241/api/ask -H 'Content-Type: application/json' \
  -d '{"question":"Чем доступность отличается от надёжности?","mode":"rag","history":[],"rerank":true,"rewrite":true}'
curl localhost:8241/api/traces
```

`mode`: `auto`, `rag`, `plain`. История — список `{role: "user" | "assistant", content: "..."}`,
не больше 12 сообщений и 30 000 символов суммарно. Старое поле `rag: true/false` поддерживается
для совместимости с просмотрщиком. Ошибки имеют вид `{"message":"..."}`.
`rerank: true/false` переопределяет настройку для одного запроса; если поле опущено, используется
`RERANKER_ENABLED` (по умолчанию `true`). В ответе `reranking` содержит модель, число кандидатов,
итоговый top-K и время этапа. `sources[].score` сохраняет косинус, `rerankScore` — отдельную оценку BGE.
`rewrite: true/false` переопределяет переформулировку для одного запроса; опущенное поле использует
`QUERY_REWRITE_ENABLED` (по умолчанию `true`). `rewriting` содержит исходный вопрос, прежний и итоговый
поисковые запросы, причину, модель, время и статус `rewritten/unchanged/disabled/fallback`.
`changed` сравнивает итоговый поисковый запрос с прежней подготовкой. Поле `retrievalMs` включает rewrite.

## Проверка

```bash
./gradlew :rag-agent:test :rag-agent:bootJar
```

Тесты проверяют цельные определения, раздельные термины глоссария, формулу вместе с расшифровкой
переменных, вводную фразу длинного списка, шапки таблиц, fenced-код, предложения и UTF-16 offsets.
Для SQLite проверяются сохранение метаданных/векторов и откат неудачной замены индекса.
Для реранкера проверяются HTTP-протокол, сопоставление индексов, порядок и сохранение косинуса,
согласованность промпта/ссылок/трассировки и отказ при неполных, повторных или некорректных оценках.
Для query rewrite проверяются история и исходная реплика, параметры отдельного вызова DeepSeek,
отсутствие вызова при выключении, сохранение чисел/перцентилей и fallback при ошибке или обрезанном JSON.

## Эксперимент с нарезкой

фиксированному индексу: обе ветки используют один вектор вопроса и один промпт генерации, меняется
только найденный контекст. История, rewriting, фильтр и reranker выключены.
Скрипт явно отправляет `rerank: false, rewrite: false`, поэтому новые этапы не меняют условия этого эксперимента.

Проверяется весь новый контекст: кроме границ изменились размер и добавление заголовков к эмбеддингам.

## Эксперимент с query rewrite

```bash
python3 tools/compare_rewrite.py
```

Те же 10 вопросов дня 22 и отдельное уточнение «А когда он не нужен?» с фиксированной историей об ADR.
В обеих ветках одинаковы структурный индекс, BGE, top-20 → top-5, история и настройки генерации;
меняется только `rewrite: false/true`. Прогон делает 22 запроса ответа и 11 запросов переформулировки.
`data/eval/rewrite-run.json` сохраняет полные ответы, источники, трассировки, запросы и настройки.
Скрипт проверяет, что поисковая формулировка поступает и в эмбеддинг, и в BGE, а генерация получает
исходный вопрос; также проверяет неизменность индекса и настроек генерации.
Попадание ожидаемого документа — диагностический показатель, не автоматическая оценка верности ответа.
Детальная ручная оценка находится в `data/eval/rewrite-comparison.md`.
В текущем прогоне обе ветки дали 9/10 верных ответов (включая корректный отказ вне корпуса).
Все 10 самостоятельных вопросов и их контекст остались без изменений; переписалось только
уточнение об ADR, на которое обе ветки ответили верно. Средний дополнительный вызов занял 1,16 с.
Прирост качества от rewrite на этом наборе не обнаружен. После нового прогона оценку нужно обновить:
`data/eval/rewrite-assessment.json` и отчёт привязаны к SHA-256 исходного JSON.
