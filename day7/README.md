# День 7 — сохранение контекста

Чат с агентом, который помнит разговор и не теряет его при перезапуске приложения.
Переписка лежит в SQLite, оттуда же собирается контекст для каждого запроса к модели.

Задание требовало хранить историю на диске и **продолжать диалог так, как будто агент
не выключался**. Это и есть смысловой центр дня, поэтому в приложении нет ни одного
места, где переписка жила бы в памяти процесса.

## Стек

| Слой | Технологии |
|---|---|
| Backend | Kotlin 2.3, Spring Boot 4.1, Gradle Kotlin DSL, JDK 21 |
| Хранилище | SQLite (`sqlite-jdbc`) + `JdbcClient` |
| Frontend | Vue 3 (CDN), дизайн-система Halo Light |
| LLM | DeepSeek, `deepseek-chat` |

## Запуск

```bash
cp .env.example .env          # и вписать свой ключ с platform.deepseek.com/api_keys
./gradlew bootRun
```

Открыть http://localhost:8086 (дни 1–6 занимают 8080–8085, приложения не конфликтуют).

История пишется в `data/day7.db`. Путь задаётся `DB_PATH` и намеренно лежит **не внутри
`build/`**: иначе `./gradlew clean` уносил бы всю переписку. Папку приложение создаёт само,
поэтому первый запуск на чистой машине просто работает.

## Проверка дня

```
$ curl -X POST localhost:8086/api/chat -d '{"text":"Меня зовут Фёдор, пишу на Kotlin."}'
  → «Мурр, привет, Фёдор. Kotlin — язык достойный…»                        remembered: 2

$ curl -X POST localhost:8086/api/chat -d '{"text":"Любимый напиток — облепиховый чай."}'
  → «Запомнил: Фёдор, Kotlin, облепиховый чай.»                            remembered: 4

$ kill <pid> && java -jar build/libs/day7-0.0.1-SNAPSHOT.jar     # новый процесс

$ curl -X POST localhost:8086/api/chat -d '{"text":"Напомни: как меня зовут, на чём пишу и что пью?"}'
  → «Фёдор, Kotlin, облепиховый чай. Память у меня кошачья — цепкая.»      remembered: 6
```

Перезагрузка страницы — не проверка: историю можно было бы держать в `localStorage`,
и такой тест прошёл бы, а задание нет. Проверка — именно убитый и поднятый заново процесс.

## Как это устроено

Модель беспамятна по своей природе: она знает ровно то, что лежит в `messages` текущего
запроса. Поэтому «помнить» здесь — это на каждом ходу заново собрать переписку и отправить
её вместе с новым вопросом.

Ключевое решение: **SQLite — единственный источник правды, копии в памяти нет вообще.**

Соблазн был держать историю в поле агента, писать в базу «на всякий случай» и загружать
её при старте. Тогда появились бы две копии одних данных и вопрос их синхронизации.
Без копии пункт задания «при перезапуске загружайте историю обратно» исчезает как отдельная
задача: загружать нечего. Приложение после рестарта ведёт себя правильно **по построению**,
а не потому что мы не забыли позвать загрузку.

Цена — один `SELECT` на ход. Единицы миллисекунд против одной-трёх секунд ожидания модели.

```
браузер ──POST /api/chat──> ChatController ──> Agent.ask(text)
                                                 │
    1. store.history()  ─────────────────────────┼──> SQLite
    2. промпт = [system: персона] + история + [user: вопрос]
    3. llm.complete(промпт)  ────────────────────┼──> DeepSeek
    4. store.append(вопрос, ответ)  транзакция   ┼──> SQLite
    5. вернуть ответ  <──────────────────────────┘
```

Порядок важен: пишем **после** ответа модели, а не до.

## Модель данных

```sql
CREATE TABLE IF NOT EXISTS message (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    role       TEXT    NOT NULL CHECK (role IN ('USER', 'ASSISTANT')),
    content    TEXT    NOT NULL,
    created_at TEXT    NOT NULL
);
```

Одна таблица, три решения внутри неё:

- **Роли только `user` и `assistant`.** Системной инструкции в базе нет: персона живёт
  в `application.yml` и подставляется при сборке запроса. Запиши её в историю — и смена
  персоны в конфиге разошлась бы с тем, что уже сохранено.
- **Порядок диалога задаёт `id`.** `AUTOINCREMENT` монотонен, значит сортировка по нему
  и есть хронология. На `created_at` сортировку не завязываем: оба сообщения одного хода
  получают близкие метки и могут совпасть.
- **Вся «миграция» — идемпотентный `schema.sql`.** `IF NOT EXISTS` позволяет гонять скрипт
  на каждом старте, так что Flyway ради одной таблицы не нужен.

## API

| Метод | Ручка | Что делает |
|---|---|---|
| `GET` | `/api/chat` | вся история и кто отвечает — фронт рисует это при открытии страницы |
| `POST` | `/api/chat` | один ход: сообщение внутрь, ответ наружу |
| `DELETE` | `/api/chat` | забыть всё |

Статусы `POST`: `200` — ответ получен и сохранён, `502` — модель не ответила (в базе при
этом не изменилось ничего), `400` — пустое сообщение.

Историю отдаёт сервер, а не хранит вкладка. Поэтому заново открытая страница показывает тот
же диалог — как и страница, открытая после перезапуска приложения.

## Что видно в логах

Логи идут в stdout — то есть в терминал, где запущено приложение (`./gradlew bootRun`).
Три уровня подробности, чтобы выбирать глубину.

**`INFO` — сводка, две строки на ход:**

```
advent.day7.agent.Agent : Ход 2: сообщений в истории: 2, блоков в промпте: 4
advent.day7.agent.Agent : Ход 2: ответ за 1127 мс, токенов 272. Сохранено, сообщений в истории: 4
```

Первые числа — то самое место, где тема дня видна глазами: история растёт, промпт растёт
вместе с ней, и расход токенов на вход тоже.

**`DEBUG` (включён по умолчанию) — внутрянка хода:** что пришло агенту на вход, из каких
блоков собран промпт (целиком, а не в обрезке) и что вернула модель.

```
┌── ХОД 2 · вход агента (15 симв.)
│  Как меня зовут?
├── ПРОМПТ МОДЕЛИ · 4 блоков, 620 симв.
│  [1] SYSTEM (489 симв.)
│       Ты кот по имени Барсик. Ты живёшь в этом чате и помогаешь людям…
│  [2] USER (26 симв.)
│       Меня зовут Фёдор. Запомни.
│  [3] ASSISTANT (90 симв.)
│       Запомнил, Фёдор. Мяу, редкое человеческое имя — звучит солидно, как стук мисок…
│  [4] USER (15 симв.)
│       Как меня зовут?
└── уходит в deepseek-chat: temperature 0.8, потолок ответа 1024 токенов

┌── ХОД 2 · ответ модели за 1127 мс (79 симв.)
│  Тебя зовут Фёдор. Я коты памятливые, особенно на имена тех, кто рядом с миской.
├── токены: вход 244 (из них из кэша провайдера 128), выход 28, всего 272
└── модель deepseek-v4-flash, остановка: stop
```

Здесь же видны две вещи, которые иначе остались бы незаметными. Провайдер отвечает
`model=deepseek-v4-flash`, хотя просили `deepseek-chat`: это его собственный алиас за
конкретной версией. И `из кэша провайдера` — растущий неизменный префикс промпта DeepSeek
кэширует, поэтому повторная отправка истории стоит дешевле, чем кажется по числу токенов.

**`TRACE` у клиента — сырые JSON:** буквально то, что ушло и пришло по сети.

```yaml
logging:
  level:
    advent.day7.llm.DeepSeekClient: TRACE
```

```
TRACE … DeepSeekClient : HTTP POST https://api.deepseek.com/chat/completions — тело запроса:
{"model":"deepseek-chat","messages":[{"role":"system","content":"Ты кот по имени Барсик…
TRACE … DeepSeekClient : HTTP 200 — тело ответа:
{"id":"0b7c1ea3…","model":"deepseek-v4-flash","choices":[{"index":0,"message":{"role":"assistant"…
```

**Что в логи не попадает никогда — API-ключ.** Он передаётся заголовком `Authorization`,
а заголовки не логируются ни на одном уровне: в `TRACE` уходит только тело запроса.

Тише — одной строкой: `logging.level.advent.day7: INFO`.

## Решения и их цена

**Историю отправляем целиком, без окна.** Задание дня — чтобы агент помнил прошлые
сообщения, и урезанное окно этому противоречило бы. Цена известна и принята осознанно:
с каждым ходом запрос растёт, и на очень длинном диалоге он упрётся в контекст модели.
Провайдер тогда ответит ошибкой, а не тихой потерей памяти — сбой будет виден, а не спрятан.
Окно, суммаризация и вытеснение старого — тема отдельного дня.

**Неудачный ход в историю не попадает.** Пишем только после ответа модели, и сразу оба
сообщения — одной транзакцией. Отсюда гарантия: в базе не может оказаться вопроса без
ответа, а «висящий» `user` без `assistant` сбивал бы модель на следующем ходу. В интерфейсе
это видно: пузырь вопроса пропадает, текст возвращается в поле ввода, рядом — сообщение,
что ход не сохранён.

**`JdbcClient`, а не Spring Data JDBC.** Репозиторий-интерфейс сэкономил бы десяток строк,
но Spring Data JDBC не поддерживает SQLite: диалекты есть для DB2, H2, HSQLDB, MariaDB,
MSSQL, MySQL, Oracle и PostgreSQL, а на неподдержанной базе приложение просто не стартует.
Пришлось бы писать свой `JdbcDialect` — то есть выбор ради экономии кода обошёлся бы
дороже того, что он экономит. Контракт `MessageStore` это изолирует: если диалект однажды
появится, меняется один файл.

**Пул из одного соединения.** У SQLite один писатель на файл, и пул размером 1 превращает
состязание за запись в честную очередь вместо `SQLITE_BUSY`. Запрос это не тормозит:
соединение занято только на время `SELECT` и `INSERT`, а самое долгое — ожидание модели —
проходит вообще без соединения.

## Чего здесь нет

**Нескольких диалогов.** Агент один на приложение, история одна. Задание просит
перезапустить и продолжить — это ровно один диалог. Список диалогов, переключение
и удаление — отдельная фича со своим UI.

**Окна контекста.** Причины выше.

**Ограничения на параллельные ходы.** Два одновременных вопроса прочитали бы историю, не
видя друг друга. Приложение однопользовательское, а интерфейс блокирует кнопку до ответа,
так что защита от этого была бы обвязкой без адресата.

**Настроек на лету.** Персона, модель и температура берутся из `application.yml`. Смена
характера в интерфейсе была темой дня 6 и памяти ничего не добавляет.

**Тестов.** По решению на этот день их нет: проверка прошла живым прогоном по сценарию
из раздела «Проверка дня» — включая перезапуск процесса, ход с битым ключом и очистку.

**Фреймворка для агентов.** Ни Spring AI, ни LangChain4j, ни Koog. Память диалога — тема
задания; фреймворк спрятал бы ровно её.

## Структура

```
src/main/kotlin/advent/day7/
  chat/    Role, Message — домен переписки
  store/   MessageStore (контракт), SqliteMessageStore (единственное место с SQL)
  llm/     LlmClient (контракт), DeepSeekClient (HttpClient + JSON), DTO API
  agent/   Agent — единственное место, где собирается промпт; AgentSettings
  web/     ChatController, DTO, обработчик ошибок
  config/  DataSource поверх SQLite, настройки провайдера и агента
resources/
  schema.sql            одна таблица, идемпотентно
  static/index.html     Vue 3, система Halo Light
data/day7.db            история диалога (в .gitignore)
```
