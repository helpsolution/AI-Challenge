# День 10 — архитектура

Задание требует трёх стратегий управления контекстом и переключателя между ними. Значит
главная сущность дня — не агент и не клиент модели, а **граница между «что помним» и «что
отправляем»**. Всё остальное строится вокруг неё.

## Откуда берём базу

Основа — **день 8**, а не день 9. В девятом дне `Agent` разросся до 532 строк, потому что
держал в себе и сборку промпта, и суммаризацию, и учёт токенов, — то есть ровно те три
обязанности, которые сегодня надо развести. Восьмой день чище, но и там половина `Agent` —
детектор урезания промпта от OpenRouter, к этому дню отношения не имеющий.

Переносим как есть: `HttpJson`, `OpenAiDtos`, `LlmException`, `DeepSeekClient`, каркас
`SqliteChatStore`, вёрстку и `system.css`.

Выкидываем целиком:

| Что | Почему |
|---|---|
| `OpenRouterClient`, `OpenRouterProperties` | провайдер один — DeepSeek |
| `LlmProperties`, `LlmConfiguration` | выбирать больше не из кого, клиент создаётся напрямую |
| детектор `compressed` в `Agent` | ловил специфику агрегатора, которого больше нет |
| `Summarizer`, `ContextAssembler`, `Summary` | конспект — тема дня 9, здесь стратегии другие |

Минус четыре файла в конфиге и минус три строки в `application.yml`, которые раньше
приходилось править согласованно (`llm.provider` + `agent.model` + `agent.context-limit`).

## Четыре кубика

```
                 ┌──────────────┐
   HTTP ────────▶│    Agent     │  ядро: один ход
                 └──────┬───────┘
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
   ContextStrategy   LlmClient    ChatStore
   что отправить    как спросить  что помним
```

`Agent` не знает, как собран промпт, и не знает, откуда взялась история. Его работа —
последовательность из четырёх шагов, и она одинакова для всех стратегий:

```kotlin
fun ask(sessionId: Long, question: String): Exchange {
    val input   = StrategyInput(session, store.history(sessionId), question)
    val context = strategy.assemble(input)          // 1. что отправляем
    val answer  = llm.complete(context.toRequest())  // 2. спрашиваем
    val exchange = store.saveTurn(...)               // 3. записываем ход и его цену
    strategy.observe(input, exchange)                // 4. даём стратегии обновить состояние
    return exchange
}
```

Четвёртый шаг — единственная неочевидная строка, и она здесь заранее: без неё стратегия
Facts не сможет обновлять свой блок ключ-значение, не протекая в агент. У Sliding Window
это пустая реализация по умолчанию.

## Интерфейс стратегии

```kotlin
interface ContextStrategy {
    val id: StrategyId

    /** Из чего собрать запрос к модели. Вызывается перед каждым ходом. */
    fun assemble(input: StrategyInput): PromptContext

    /** Обновить своё состояние после удачного хода — и сказать, чего это стоило. */
    fun observe(input: StrategyInput, answer: Message): Upkeep? = null
}

data class StrategyInput(
    val session: Session,
    val history: List<Message>,
    val question: String,
)

data class PromptContext(
    val blocks: List<ApiMessage>,
    /** Сколько сообщений истории вошло в промпт дословно. */
    val includedMessages: Int,
    /** Сколько отброшено. Главное число дня: именно оно отличает стратегии. */
    val droppedMessages: Int,
    /** Чем стратегия дополнила промпт помимо истории: блок фактов, метка ветки. */
    val note: String? = null,
)
```

`PromptContext` возвращает не только блоки, но и разбор состава. Без разбора сравнение
стратегий сводится к разглядыванию ответов — а разглядывание всегда показывает, что все
три работают прилично.

## Почему Branching здесь не стратегия

Sliding Window и Facts отвечают на вопрос «что из истории отправить модели». Ветки отвечают
на другой вопрос — «какая история вообще считается текущей». Они ортогональны: ветвиться
можно и со скользящим окном, и с фактами.

Если засунуть ветки в `ContextStrategy`, в интерфейс придётся добавить `checkpoint`,
`fork` и `switch` — команды, к сборке промпта отношения не имеющие, и пустые у двух
реализаций из трёх. Интерфейс поплывёт ровно так, как поплыл `Agent` в девятом дне.

Решение: ветки живут в хранилище (форк = новая сессия), а в переключателе `BRANCHING` —
это скользящее окно плюс разблокированная панель веток. Три пункта в переключателе, как
требует задание, без вранья в архитектуре.

## Схема БД

```sql
CREATE TABLE session (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    title         TEXT    NOT NULL,
    strategy      TEXT    NOT NULL,   -- SLIDING_WINDOW | FACTS | BRANCHING
    window_size   INTEGER NOT NULL,   -- параметр стратегии, снимок на момент создания
    created_at    TEXT    NOT NULL,
    -- ветвление: откуда отпочковались и после какого сообщения родителя
    parent_id     INTEGER REFERENCES session(id),
    forked_after  INTEGER
);

CREATE TABLE message (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id INTEGER NOT NULL REFERENCES session(id),
    role       TEXT    NOT NULL CHECK (role IN ('USER', 'ASSISTANT')),
    content    TEXT    NOT NULL,
    created_at TEXT    NOT NULL
);

CREATE TABLE turn (...);  -- как в дне 8, плюс session_id и состав промпта
```

Форк — это одна вставка, а не обход дерева:

```sql
INSERT INTO message (session_id, role, content, created_at)
SELECT :newSession, role, content, created_at
FROM message WHERE session_id = :parent AND id <= :checkpoint;
```

Дерева сообщений с `parent_id` сознательно нет: оно экономит несколько десятков строк
ценой рекурсивного CTE в каждом чтении истории и усложнения всего остального кода.
Копия сообщений при форке — плата, которой на этих объёмах не существует.

## Настройки

Значения по умолчанию — в `application.yml`. Стратегия и её параметры **записываются
в сессию при создании** и дальше не меняются:

```yaml
agent:
  name: Барсик
  model: ${AGENT_MODEL:deepseek-chat}
  context-limit: ${AGENT_CONTEXT_LIMIT:1000000}
  max-tokens: 1024
  temperature: 0.7
  persona: >
    ...
  context:
    strategy: SLIDING_WINDOW
    # Сколько последних сообщений уходит дословно. Шесть — это три пары «вопрос-ответ».
    window-size: 6
```

Отсюда важное свойство: в одной сессии не может оказаться перемешанной истории от разных
стратегий. Переключатель в интерфейсе создаёт **новую** сессию, а не меняет режим текущей,
иначе сравнение считалось бы по ходам, часть которых прошла в другом режиме.

### Про размер окна

У `deepseek-chat` контекст 1 000 000 токенов. На пятнадцати сообщениях **никакая стратегия
ничего не потеряет** — разницы между ними просто не будет видно. Поэтому окно ставим
заведомо тесным: `window-size: 6`. К концу сценария начало разговора выйдет из окна,
контрольные вопросы про ранние детали начнут проваливаться, и станет видно то, что Facts
потом должен вылечить.

Это не подгонка эксперимента, а его условие: без тесного окна замер показывает не свойства
стратегии, а размер контекста модели.

## Сценарий как измерительный прибор

`src/main/resources/scenario/tz-brief.json` — пятнадцать реплик пользователя плюс восемь
контрольных вопросов. Детали проекта названы в разное время: контакт заказчика и СУБД
в начале, категории уведомлений в середине, роли из LDAP под конец. У каждой проверки
записан `plantedAtStep` — на каком шаге факт прозвучал.

Прогон: `POST /api/scenario/run` создаёт сессию под выбранную стратегию, проигрывает все
пятнадцать реплик, затем задаёт контрольные вопросы и сверяет ответы с `expect`
(вхождение подстроки без учёта регистра) и `forbid` (подстрока, которой быть не должно —
ловит выдуманный SMS-канал).

На выходе по каждой стратегии:

| Что меряем | Откуда |
|---|---|
| удержание деталей | доля пройденных проверок, с разбивкой по `plantedAtStep` |
| расход | сумма `prompt_tokens` / `completion_tokens` по ходам |
| цена | по прайсу DeepSeek из конфига, как в дне 8 |
| размер промпта | `includedMessages` / `droppedMessages` по ходам |
| задержка | медиана `latency_ms` |

Разбивка по `plantedAtStep` — та колонка, ради которой всё затевалось: она показывает
не «стратегия хуже», а **где именно** она теряет память.

Оценка ключевыми словами, а не LLM-судьёй: судья добавил бы недетерминированность в сам
измерительный прибор, а факты в сценарии подобраны конкретные — `PostgreSQL`, `15 марта`,
`LDAP`, `500`.

## Что делаем сегодня, что откладываем

**Сделано:** каркас, `SlidingWindowStrategy`, `FactsStrategy`, прогон сценария, отчёт
сравнения. Схема БД рассчитана на три стратегии с самого начала — `strategy` в сессии,
`parent_id` и `forked_after`, — поэтому Facts не потребовал переписывать хранилище:
добавились две таблицы (`fact`, `upkeep`) и строка в реестре.

**Дальше:** панель веток поверх форка сессии — механизм работает и используется прогоном
сценария, не хватает управления из интерфейса. И сценарий подлиннее: пятнадцать реплик
не дотягивают до перелома, на котором досье начинает окупаться.

## Чем это может не сработать

- **Окно в 6 сообщений может оказаться слишком тесным**: агент начнёт переспрашивать уже
  на восьмом шаге, и сценарий развалится не там, где мы хотели посмотреть. Настраивается
  одним числом в конфиге; ориентир — чтобы провалились ранние проверки, но диалог доехал
  до конца.
- **Проверка подстрокой ловит форму, а не смысл.** «Мы не обсуждали СУБД, но обычно берут
  PostgreSQL» засчитается как успех. Риск снижен тем, что вопросы прямые, а факты редкие,
  но полностью не снят.
- **Кэш префикса DeepSeek исказит сравнение цены.** У скользящего окна префикс меняется
  каждый ход, у полной истории — нет, поэтому дешевле по токенам не значит дешевле
  по деньгам. В отчёте цену и токены надо показывать раздельно, а не сводить в одно число.
