# День 6 — первый агент

Чат с агентом, у которого есть имя, характер, память и настроение. Слева диалог,
справа видно, что агент делает с каждым вопросом: что вспомнил, из чего собрал промпт,
через сколько миллисекунд пришёл первый токен, сколько это стоило в токенах.
Настройки — персона, модель, температура, окно памяти — меняются на лету, память при этом
сохраняется.

Задание требовало, чтобы агент был **отдельной сущностью, а не одним вызовом API**.
Это и есть смысловой центр дня, поэтому граница проведена жёстко и видна в интерфейсе.

## Стек

| Слой | Технологии |
|---|---|
| Backend | Kotlin 2.3, Spring Boot 4.1, Gradle Kotlin DSL, JDK 21 |
| Frontend | Vue 3 (CDN), дизайн-система Halo Light |
| LLM | DeepSeek — `deepseek-chat` и `deepseek-reasoner`, потоковый режим |

## Запуск

```bash
cp .env.example .env          # и вписать свой ключ с platform.deepseek.com/api_keys
./gradlew bootRun
```

Открыть http://localhost:8085 (дни 1–5 занимают 8080–8084, приложения не конфликтуют).

## Чем агент отличается от вызова API

Вызов API заканчивается вместе с ответом. Агент — нет: он живёт столько же, сколько
приложение, и между вопросами у него остаётся состояние.

| | Вызов API | Агент дня 6 |
|---|---|---|
| Время жизни | один запрос | всё время работы приложения |
| Контекст | приходит снаружи целиком | собирает сам из своей памяти |
| Настройки | в каждом запросе | свои, меняются отдельной операцией |
| Наблюдаемость | статус и тело ответа | поток событий по каждому шагу |
| Ответ | одна строка в конце | токены по мере генерации |

`Agent` (`agent/Agent.kt`) — обычный Kotlin-класс. Он не знает ни про Spring, ни про HTTP,
ни про браузер: единственная зависимость — интерфейс `LlmClient`. Всё, что он умеет, — это
четыре операции: `ask`, `reconfigure`, `forget`, `snapshot`. Контроллер ничего не решает
сам, он только перекладывает события агента в server-sent events.

```
ask(вопрос) → Flow событий:
  StateChanged(THINKING) → Step(вспомнил контекст) → Step(собрал промпт)
  → Step(отправил) → Token(«М») → Token(«ур») → … → Completed(протокол хода)
```

## Память

Память разделена на две вещи, и разница между ними показана в интерфейсе цифрами.

**Что агент помнит** — вся стенограмма диалога. Нужна интерфейсу: после перезагрузки
страницы диалог восстанавливается из памяти агента, а не из браузера.

**Что он держит в голове прямо сейчас** — только последние `memoryWindow` ходов. Именно
они уходят в промпт. Окно 10 ходов при 40 сообщениях в памяти означает, что модель увидит
20 последних, а не все 40.

Окно 0 превращает агента в то, чем он был бы без памяти: каждый вопрос как первый.
Это самый быстрый способ увидеть, что память — не украшение. Спросите имя, поставьте 0,
спросите снова.

## Настроение

Настроение не выдумывается и не спрашивается у модели — оно **выводится из измеримых
сигналов**, поэтому у каждого состояния аватара есть проверяемая причина.

| Настроение | Причина |
|---|---|
| 😴 дремлет | ходов ещё не было или в диалоге тихо дольше двух минут |
| 👀 насторожился | вопрос получен, первого токена ещё нет |
| 💬 отвечает | текст идёт прямо сейчас |
| 😾 не в духе | последний ход закончился сбоем |
| 🥱 устал | последний ответ занял больше 15 секунд |
| 😺 доволен | всё в порядке |

Аватар — inline-SVG в том же контурном языке, что и дизайн-система: уши, глаза, усы, хвост
и рот анимируются CSS по двум data-атрибутам. Готовых Lottie- или Rive-ассетов нет
намеренно: сторонний файл с непонятной лицензией дал бы то же самое, но с зависимостью.

## Стриминг

Ответ идёт потоком на всём пути: SSE от DeepSeek → события агента → SSE в браузер.
Первый токен приходит за 0,5–1 секунду вместо 3–6 секунд ожидания полного ответа.

Два следствия, которые пришлось учесть в коде:

- **Расход токенов в стриме не приходит сам.** Нужен `stream_options.include_usage` —
  иначе провайдер присылает только текст, и считать токены будет нечем.
- **Повтор при сетевом сбое допустим только до первого токена.** Дальше повтор склеил бы
  два ответа в один, поэтому `DeepSeekClient` считает отданные наружу дельты и после
  первой из них уже не повторяет.

Если браузер закрыл вкладку посреди ответа, поток замолкает, но агента это не прерывает:
ход обязан дойти до памяти, иначе после перезагрузки в диалоге окажется дыра.

## Чего здесь нет

**Инструментов.** Агент не умеет вызывать функции, искать в интернете и ходить по шагам
к цели. Задание этого не просит, а «агент» в смысле tool-use — тема отдельного дня.

**Нескольких диалогов.** Агент один на приложение. Это делает его состояние наблюдаемым:
журнал, счётчики и память относятся к нему, а не к сессии браузера. Обратная сторона —
он отвечает по одному вопросу за раз, и параллельный запрос получает 409.

**Фреймворка для агентов.** Ни Spring AI, ни LangChain4j, ни Koog. Задание просит написать
агента и инкапсулировать в нём логику — фреймворк спрятал бы ровно это.

**Тестов.** По решению на этот день их нет намеренно: проверка прошла живым прогоном
по сценарию в `swarm-report/day6-first-agent-e2e-scenario.md`.

## API

| Метод | Ручка | Что делает |
|---|---|---|
| `GET` | `/api/agent` | снимок агента: состояние, настроение, настройки, память, статистика, журнал |
| `POST` | `/api/agent/chat` | ход агента потоком SSE: `state`, `step`, `token`, `reasoning`, `done`, `error` |
| `PUT` | `/api/agent/settings` | перенастроить на лету, память сохраняется |
| `DELETE` | `/api/agent/memory` | забыть диалог |
| `GET` | `/api/presets` | заготовки персон |

Настройки проверяет сам агент (`AgentSettings.validate`), а не DTO контроллера: сущность
обязана защищать себя сама, откуда бы настройки ни пришли — из конфига, из API или из теста.
Модель выбирается только из белого списка в `application.yml`, произвольная строка с фронта
во внешний API не уходит. Ключ читается из `.env` и на фронт не попадает никогда.
