# День 6 — первый агент

Чат с агентом, у которого есть имя, характер и настроение. Слева диалог, справа видно,
что агент сделал с каждым вопросом: из чего собрал промпт, что отправил модели, сколько
это заняло и во сколько токенов обошлось. Настройки — персона, модель, температура,
потолок ответа — меняются на лету.

Задание требовало, чтобы агент был **отдельной сущностью, а не одним вызовом API**.
Это и есть смысловой центр дня, поэтому граница проведена жёстко и видна в интерфейсе.

## Стек

| Слой | Технологии |
|---|---|
| Backend | Kotlin 2.3, Spring Boot 4.1, Gradle Kotlin DSL, JDK 21 |
| Frontend | Vue 3 (CDN), дизайн-система Halo Light |
| LLM | DeepSeek — `deepseek-chat` и `deepseek-reasoner` |

## Запуск

```bash
cp .env.example .env          # и вписать свой ключ с platform.deepseek.com/api_keys
./gradlew bootRun
```

Открыть http://localhost:8085 (дни 1–5 занимают 8080–8084, приложения не конфликтуют).

## Чем агент отличается от вызова API

Вызов API заканчивается вместе с ответом. Агент — нет: он живёт столько же, сколько
приложение, и между вопросами у него остаётся состояние.

| | Вызов API | Агент дня 6 |
|---|---|---|
| Время жизни | один запрос | всё время работы приложения |
| Настройки | в каждом запросе | свои, меняются отдельной операцией |
| Промпт | приходит снаружи готовым | собирает сам из своей персоны и вопроса |
| Что возвращает | текст ответа | текст и протокол хода: шаги, время, токены |
| Следы | никаких | счётчики и журнал жизни |
| Границы | заданы вызывающим | защищает себя сам: белый список моделей, один ход за раз |

`Agent` (`agent/Agent.kt`) — обычный Kotlin-класс. Он не знает ни про Spring, ни про HTTP,
ни про браузер: единственная зависимость — интерфейс `LlmClient`. Всё, что он умеет, — это
три операции: `ask`, `reconfigure`, `snapshot`.

```
ask(вопрос) → TurnReport
  шаги:  получил вопрос → собрал промпт → отправил модели → получил ответ
  плюс:  текст ответа, модель, время, расход токенов, причина остановки
```

Сбой модели не бросается исключением наружу, а становится частью протокола: ход
состоялся, просто закончился неудачей. Иначе счётчики и журнал агента расходились бы
с тем, что видел пользователь.

Контроллер ничего не решает сам — отдаёт протокол как есть, добавляя к нему свежий снимок
агента.

## Один запрос, один ответ

Отправили вопрос, дождались ответа, показали. Ни стриминга по токенам, ни server-sent
events, ни промежуточных состояний.

Сначала здесь был стриминг: SSE от провайдера, поток событий агента, SSE в браузер,
курсор печати в пузыре. Работало, но задание дня — принять запрос, отправить его в LLM,
получить ответ и показать результат. Стриминг к этому добавлял три слоя транспорта, ради
которых у агента появлялись события, состояние «отвечает» и разбор потока на фронте.
Убрали — и вместе с ним ушли `AgentEvent`, `SseEmitter`, чтение потока в браузере
и шестьдесят строк кода. Продвинутая версия — тема отдельного дня.

Цена простоты: первые слова ответа появляются не через секунду, а вместе со всем текстом,
через одну-три секунды на `deepseek-chat`. Пока ждём, кот насторожен и подрагивает усами,
а в ленте стоят три точки.

Что при этом всё равно пришлось учесть:

- **Ожидание ответа обязано иметь границу.** `RestClient` с `JdkClientHttpRequestFactory`
  её не поставил: запрос, на который провайдер не ответил, висел дольше заданных трёх минут
  и держал агента заблокированным навсегда — все следующие вопросы получали 409. Поэтому
  клиент работает с `java.net.http.HttpClient` напрямую, где границу задаёт
  `HttpRequest.timeout`. Заодно ушёл лишний слой: тело запроса тут собирается строкой,
  ответ разбирается один раз, и посредник ничего не добавлял.
- **Таймаут не повторяется, обрыв соединения — повторяется.** Второе ожидание будет таким
  же долгим, а вот разорванное соединение лечится повтором: ответа мы не получили,
  дублировать нечего.

## Памяти диалога здесь нет — и это осознанно

Каждый вопрос независим: в промпт уходит персона и один вопрос, больше ничего. В шапке
диалога об этом сказано прямо, потому что растущая лента сообщений на экране легко создаёт
обратное впечатление.

Задание дня память диалога не просит, а контекст между ходами — отдельная тема со своими
решениями: окно, суммаризация, вытеснение старого. Идти от простого к сложному значит
не тащить её в день, где она не требуется.

Лента сообщений живёт только в открытой вкладке: перезагрузка страницы её очищает. Это не
недоделка, а честное отражение того, что переписки для агента не существует. Счётчики
и журнал при этом остаются — они про агента, а не про диалог.

## Настроение

Настроение не выдумывается и не спрашивается у модели — оно **выводится из измеримых
сигналов**, поэтому у каждого состояния аватара есть проверяемая причина.

| Настроение | Причина |
|---|---|
| 😴 дремлет | ходов ещё не было или в диалоге тихо дольше двух минут |
| 👀 насторожился | вопрос ушёл модели, ответа ещё нет |
| 😾 не в духе | последний ход закончился сбоем |
| 🥱 устал | последний ответ занял больше 15 секунд |
| 😺 доволен | всё в порядке |

Аватар — inline-SVG в том же контурном языке, что и дизайн-система: уши, глаза, усы, хвост
и язык анимируются CSS по двум data-атрибутам. Готовых Lottie- или Rive-ассетов нет
намеренно: сторонний файл с непонятной лицензией дал бы то же самое, но с зависимостью.

## Чего здесь нет

**Стриминга.** Причины выше. Задание просит получить ответ, а не показывать его по мере
генерации.

**Памяти диалога.** Тоже выше: контекст между ходами — тема следующих дней.

**Инструментов.** Агент не умеет вызывать функции, искать в интернете и ходить по шагам
к цели. «Агент» в смысле tool-use — ещё один отдельный день.

**Нескольких диалогов.** Агент один на приложение. Это делает его состояние наблюдаемым:
журнал и счётчики относятся к нему, а не к сессии браузера. Обратная сторона — он отвечает
по одному вопросу за раз, и параллельный запрос получает 409.

**Фреймворка для агентов.** Ни Spring AI, ни LangChain4j, ни Koog. Задание просит написать
агента и инкапсулировать в нём логику — фреймворк спрятал бы ровно это.

**Тестов.** По решению на этот день их нет намеренно: проверка прошла живым прогоном
по сценарию в `swarm-report/day6-first-agent-e2e-scenario.md`.

## API

| Метод | Ручка | Что делает |
|---|---|---|
| `GET` | `/api/agent` | снимок агента: состояние, настроение, настройки, статистика, журнал |
| `POST` | `/api/agent/chat` | один ход: вопрос внутрь, протокол хода и снимок агента наружу |
| `PUT` | `/api/agent/settings` | перенастроить на лету |
| `GET` | `/api/presets` | заготовки персон |

Статусы `/api/agent/chat`: `200` — ход удался, `502` — ход состоялся, но модель не ответила
(тело того же вида, шаги показывают, на чём оборвалось), `409` — агент занят другим
вопросом, `400` — пустое сообщение.

Настройки проверяет сам агент (`AgentSettings.validate`), а не DTO контроллера: сущность
обязана защищать себя сама, откуда бы настройки ни пришли — из конфига, из API или из теста.
Модель выбирается только из белого списка в `application.yml`, произвольная строка с фронта
во внешний API не уходит. Ключ читается из `.env` и на фронт не попадает никогда.
