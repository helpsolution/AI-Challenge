# Песочница: бронирование переговорок

Маленький Spring Boot сервис, на котором показываем AI-ревью: демо-PR меняют этот код, а ревьюер проверяет их по правилам ниже.

```bash
cd day32
./gradlew :sandbox:bootRun        # http://localhost:8320
```

## API

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/rooms/{roomId}/bookings` | брони переговорки по времени начала |
| `POST` | `/api/rooms/{roomId}/bookings` | создать бронь: `{"start": "...Z", "end": "...Z"}`, автор в заголовке `X-User` |
| `DELETE` | `/api/rooms/{roomId}/bookings/{id}` | отменить бронь, автор в заголовке `X-User` |
| `GET` | `/api/rooms/{roomId}/free?date=2026-10-14&minutes=60` | свободные окна на сутки UTC |

Ошибки возвращаются как `ProblemDetail`: 400 — неверная бронь, 403 — чужая бронь, 404 — нет брони, 409 — конфликт по времени.

## Правила предметной области

1. Бронь — полуинтервал `[start, end)`. Встреча до 11:00 и встреча с 11:00 не пересекаются. Пересечение считает только `Booking.overlaps`, на нём же построен поиск свободных окон в `RoomAvailability`.
2. Бронь длится от 15 минут до 4 часов. Начало и конец кратны 15 минутам.
3. Изменить или отменить бронь может только её автор. Начавшуюся бронь не меняют и не отменяют.
4. Время хранится и передаётся в UTC как `Instant`. Текущее время берётся только из бина `Clock`, часовые пояса — забота клиента.
5. Проверка пересечений и запись брони выполняются под одной блокировкой (`@Synchronized` в `BookingService`), иначе две брони займут одно время.

## Устройство

- `BookingController` — только HTTP: разбирает запрос и вызывает сервис. Бизнес-правила и проверки живут в `BookingService`.
- `BookingService` — создание и отмена, все проверки из правил 2–5.
- `RoomAvailability` — свободные окна на сетке 15 минут.
- `BookingRepository` — хранилище в памяти.
- `NotificationClient` — вебхук о событиях брони. Токен берётся из `NOTIFY_TOKEN` и никогда не пишется в лог. Сбой уведомления не отменяет бронь: пишем предупреждение и идём дальше.
