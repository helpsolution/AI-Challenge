# День 21 — Индексация документов

RAG-пайплайн собирается по кубикам: **текст → вектор** через локальную Ollama, **текст → чанки** двумя
стратегиями — по фиксированному размеру и по структуре — и **индекс**: корпус Markdown-документов, нарезанный
каждой стратегией, с эмбеддингами и метаданными в двух базах SQLite. Поиска по индексу пока нет.

## Запуск

Нужны JDK 21+ и Ollama с моделью эмбеддингов:

```bash
brew install ollama
brew services start ollama        # сервер в фоне на http://localhost:11434
ollama pull nomic-embed-text      # ~270 МБ, 768 измерений

cd day21
./gradlew :rag-service:bootRun
```

- **Swagger:** http://localhost:8230/swagger
- OpenAPI: http://localhost:8230/api-docs

Сервис слушает только `127.0.0.1`. Ключей не нужно: данные не покидают компьютер.

| Переменная           | По умолчанию             |
|----------------------|--------------------------|
| `OLLAMA_BASE_URL`    | `http://localhost:11434` |
| `OLLAMA_EMBED_MODEL` | `nomic-embed-text`       |
| `PORT`               | `8230`                   |

## Корпус

Документы для индекса — Markdown-файлы в `data/corpus/`. В репозиторий корпус не входит: `data/` в `.gitignore`.
В начале файла может быть шапка YAML — из неё берутся `title` и `url`, а в чанки идёт только текст под ней:

```markdown
---
title: "Введение"
url: "https://example.com/intro"
---

# Введение
…
```

## Эмбеддинги

```bash
curl -s localhost:8230/api/embeddings -H 'Content-Type: application/json' \
  -d '{"texts": ["кот", "собака", "автомобиль"]}'
```

В ответе — модель, размерность, число прочитанных токенов, время и по элементу на каждый текст:
`index`, `text`, `norm` (длина вектора) и сам `vector`.

## Чанкинг по фиксированному размеру

```bash
curl -s 'localhost:8230/api/chunking/fixed-size?chunkSize=500&overlap=50' \
  -H 'Content-Type: text/plain' --data-binary @../day20/README.md
```

Тело — обычный текст, не JSON: в Swagger можно вставить документ как есть. Окно в `chunkSize` символов
шагает с шагом `chunkSize − overlap`; перекрытие видно по `start`/`end` соседних чанков.

Размер — в символах, а не в токенах, как в лекции: токенизатора модели на JVM нет. Для ориентира:
чанк в 500 символов русского текста — это 380–415 токенов nomic-embed-text, README с кодом — 230–415.
Контекст модели — 2048 токенов, то есть примерно 2500 символов по-русски.

## Чанкинг по структуре

```bash
curl -s 'localhost:8230/api/chunking/structural?maxChunkSize=1000' \
  -H 'Content-Type: text/plain' --data-binary @../day20/README.md
```

Markdown режется по заголовкам: раздел — чанк, путь заголовков («Кубики › Чанкинг») — в поле `section`.
`#` внутри блока кода заголовком не считается. Раздел из одного заголовка отдельным чанком не становится:
его имя и так есть в пути вложенных разделов.

Раздел длиннее `maxChunkSize` делится по всё более мелким границам: абзацы → строки → символы.
Соседние куски склеиваются, пока влезают; заголовок не отрывается от текста под ним. По символам режется
только кусок без абзацев и строк — и поровну, без огрызка в конце. Текст без заголовков, например код,
делится так же. Перекрытия нет: границы и так проходят между законченными кусками.

## Метаданные чанков

Шапка YAML — метаданные, а не текст: `Document.parse` забирает из неё `title` и `url`, в чанки идёт только
текст под шапкой, одинаково для обеих стратегий. У каждой стратегии своя модель чанка:

| Поле | `FixedSizeChunk` | `StructuralChunk` | Пример |
|---|---|---|---|
| `chunkId` | ✓ | ✓ | `data/corpus/intro.md#0` |
| `source` | ✓ | ✓ | `data/corpus/intro.md` |
| `title` | ✓ | ✓ | `Введение` — из шапки, без шапки — имя файла |
| `url` | ✓ | ✓ | `https://example.com/intro`, без шапки — `null` |
| `section` | — | ✓ | `Введение › Установка` |
| `index`, `start`, `end`, `text` | ✓ | ✓ | номер и границы в тексте без шапки |

`chunkId` — путь к файлу и номер чанка: детерминированный, повторная нарезка того же файла даёт те же id.
Стратегии в нём нет: чанки разных стратегий хранятся раздельно. Обе стратегии реализуют `Chunker<T>`
со `split(document)`, параметры задаются в конструкторе. В Swagger параметр `source` задаёт путь документа,
а в тело можно вставить файл целиком, вместе с шапкой.

## Индекс

```bash
curl -s -X POST 'localhost:8230/api/index/rebuild?chunkSize=500&overlap=50&maxChunkSize=1000'
curl -s localhost:8230/api/index/structural      # что легло в базу, без векторов
```

`POST /api/index/rebuild` читает все `*.md` из `data/corpus/`, режет их обеими стратегиями, считает эмбеддинги
(одна пачка на документ, с префиксом `search_document: `) и заново пишет два файла:

```
data/index/fixed-size.db   chunks(chunk_id PK, source, title, url, chunk_index, start_offset, end_offset, text, embedding)
data/index/structural.db   chunks(… то же, плюс section …)
                           meta(key, value): model, dimensions, document_prefix, параметры нарезки, built_at
```

Вектор лежит в `embedding` как 768 чисел float32 little-endian — 3 КБ на чанк. `meta` нужна будущему поиску:
вопрос надо кодировать той же моделью и парным префиксом. Всё считается в памяти и только потом пишется,
так что упавшая Ollama не портит старый индекс. Базы можно открыть в IDEA (Database → SQLite) или `sqlite3`:

```sql
SELECT chunk_id, section, length(text) FROM chunks WHERE source = 'data/corpus/intro.md';
```

Пересборка корпуса из 14 документов (≈84 тыс. символов), параметры по умолчанию:

| | fixed-size.db | structural.db |
|---|---|---|
| Чанков | 193 | 162 |
| Длина, символов: средняя / мин / макс | 483 / 51 / 500 | 511 / 69 / 992 |
| Токенов прочитано моделью | 70 022 | 62 463 |
| Эмбеддинги, с | 7,9 | 6,9 |
| Размер файла | 924 КБ | 812 КБ |

Фиксированная стратегия читает на 12% больше токенов: перекрытие кодирует каждый стык дважды.

## Устройство

```
advent/rag/
├── embedding/                  кубик «текст → вектор»
│   ├── EmbeddingClient.kt      логика: проверка входа, запрос к Ollama, перевод её ошибок
│   ├── Embeddings.kt           что кубик отдаёт наружу: векторы, токены, время
│   ├── OllamaDtos.kt           формат запросов и ответов Ollama, за пакет не выходит
│   └── OllamaConfiguration.kt  адрес, модель, таймауты и RestClient
├── chunking/                   кубик «текст → чанки»
│   ├── Chunker.kt              интерфейс стратегии: split(document) → чанки своего типа
│   ├── FixedSizeChunk.kt       модель чанка фиксированного размера
│   ├── FixedSizeChunker.kt     окно фиксированного размера с перекрытием
│   ├── StructuralChunk.kt      модель чанка по структуре, с section
│   └── StructuralChunker.kt    заголовки → абзацы → строки → символы
├── document/
│   └── Document.kt             файл → source, title, url и текст без шапки YAML
├── index/                      кубик «корпус → две базы SQLite»
│   ├── Indexer.kt              корпус → чанки → эмбеддинги → запись, отчёт по стратегиям
│   ├── FixedSizeIndex.kt       схема, запись и чтение fixed-size.db
│   ├── StructuralIndex.kt      схема, запись и чтение structural.db
│   ├── Sqlite.kt               общее: пересоздание файла, meta, вектор → BLOB
│   └── IndexProperties.kt      где корпус и где базы
└── web/                        HTTP-песочница для Swagger
    ├── EmbeddingController.kt, EmbeddingDtos.kt
    ├── ChunkingController.kt, ChunkingDtos.kt, ChunkingSamples.kt
    ├── IndexController.kt
    └── ApiExceptionHandler.kt  исключения → 400 / 415 / 502 с понятным текстом
```

Эмбеддинги и чанкинг друг о друге не знают; индексатор вызывает их напрямую, а не через HTTP.

## Что выяснилось по ходу

- **`/api/embed`, а не `/api/embeddings` из лекции.** Новый эндпоинт принимает пачку текстов и отдаёт
  векторы уже нормированными: длина 1.0 против ~22 у старого. Для нормированных векторов косинусное
  сходство — просто скалярное произведение.
- **Ollama молча обрезает длинный текст.** По умолчанию всё, что не влезло в контекст (2048 токенов
  у nomic-embed-text), отбрасывается, и приходит вектор начала текста. Сервис передаёт `truncate: false`,
  поэтому такой текст возвращается ошибкой 400 — это граница размера чанка.
- **Пустая строка** даёт ответ 200 без вектора: порядок ответов бы съехал, поэтому сервис её не пускает.
- **Близость слов модель различает слабо.** Косинус «кот·собака» 0.560 против «кот·автомобиль» 0.533;
  по-английски чуть лучше: cat·dog 0.602 против cat·car 0.558. nomic-embed-text — в основном
  англоязычная модель; для русского корпуса стоит сравнить с многоязычной.
- **Префиксы задачи.** nomic-embed-text обучали с `search_document:` для документов и `search_query:`
  для вопросов — пример с префиксами есть в Swagger.
- **Фиксированный размер режет вслепую** — посреди предложения и слова, это видно на стыках чанков
  в Swagger. Перекрытие повторяет конец чанка в начале следующего, чтобы разорванная мысль целиком
  попала хотя бы в один из них.
- **Эмодзи не разрезаются.** В Java они занимают два `char`; если граница попала между ними, она
  сдвигается на один символ, и чанк выходит на символ длиннее. Смещения `start`/`end` — в единицах
  UTF-16, как у строк Java и JavaScript.
- **Сравнение стратегий на корпусе.** 14 документов, ≈84 тыс. символов без шапок, параметры по умолчанию:
  фиксированный размер (500/50) дал 193 чанка и разрезал слово на 217 границах, структурный (предел 1000) —
  162 чанка и ни одного разрезанного слова. Длинный список без заголовков и пустых строк структурная
  стратегия делит по целым пунктам, фиксированная — посреди слов.
- **Шапка YAML — метаданные, а не текст.** Пока её резали вместе с документом, она становилась отдельным
  чанком из служебных полей. Теперь её разбирает `Document` до нарезки — одинаково для обеих стратегий,
  иначе сравнение было бы нечестным.
